00

ディレクトリ構成

モノレポ構成で、各サービス内部は Clean Architecture の4層に分割します。proto/ と gen/ を分けることで「人が書く定義」と「自動生成物」を区別しています。

go_study/
├── docker-compose.yml
├── .github/workflows/          # CI/CD (test / lint / build)
│
├── proto/                     # gRPC の共通定義（サービス間で共有／詳細は proto設計ページ）
│   ├── auth/auth.proto
│   ├── user/user.proto
│   └── task/task.proto
│
├── gen/                       # protoc が自動生成した Go コード (.pb.go)
│
├── services/
│   ├── gateway/                # API Gateway
│   │   ├── cmd/main.go          # エントリーポイント
│   │   ├── internal/handler/    # HTTP ハンドラ（ルーティング）
│   │   ├── internal/middleware/ # JWT 検証・ロギング・CORS
│   │   ├── internal/client/     # 各サービスへの gRPC クライアント
│   │   └── openapi/swagger.yaml
│   │
│   ├── auth-service/
│   │   ├── cmd/main.go
│   │   └── internal/
│   │       ├── domain/          # Entity（User, Token）純粋なビジネスモデル
│   │       ├── usecase/         # ログイン処理・トークン発行のロジック
│   │       ├── repository/      # DB アクセスの「インターフェース」
│   │       ├── infrastructure/  # DB実装・Redis実装
│   │       └── grpc/            # gRPC サーバー実装
│   │
│   ├── user-service/            # auth-service と同様の構成
│   └── task-service/             # auth-service と同様の構成
│
├── frontend/                   # React + TypeScript
│   └── src/{api, components, pages, hooks}/
│
└── pkg/                         # サービス横断の共通ライブラリ
    └── {logger, jwtutil}/

各サービスは独立した Go モジュール（go.mod）を持つか、Workspace 機能（go.work）でまとめて管理します。依存の向きは常に「外側 → 内側」で、domain は DB のことを一切知りません。

01

関数の役割（初心者向け）

Auth Service を例に、Clean Architecture の各層でどんな関数が登場するかを見ていきます。他サービスも同じパターンです。依存は必ず外側（Handler）から内側（Repository）へ向かいます。

① Handler外部との窓口
func LoginHandler(c *gin.Context)

ブラウザから来た JSON（メール・パスワード）を受け取り、UseCase 層に渡すだけ。

業務ロジックはここに書かない ― 「翻訳係」に徹する。

② UseCaseビジネスロジック
func (u *AuthUseCase) Login(ctx context.Context, email, password string) (string, error)

Repository でユーザーを探す → bcrypt でパスワードを検証 → 一致したら JWT を発行する。

DB が MySQL か PostgreSQL かは知らない。interface だけを見て呼び出すのでテストしやすい。

③ Repository契約（interface）
type UserRepository interface { FindByEmail(ctx context.Context, email string) (*User, error) }

「ユーザーを探せる」という契約を定義するだけで、中身の実装は書かない。

④ Infrastructure実際の DB/Redis 接続
func (r *mysqlUserRepository) FindByEmail(ctx context.Context, email string) (*User, error)

database/sql で実際に SQL を発行し、結果を Go の構造体に詰め替える。Repository interface の「実装」がここにある。

⑤ gRPC Serverサービス間の受け口
func (s *AuthGRPCServer) Login(ctx context.Context, req *pb.LoginRequest) (*pb.LoginResponse, error)

Gateway からの gRPC リクエストを受け取り、UseCase 層の Login を呼ぶだけの薄いアダプター（Handler 層の gRPC版）。リクエスト／レスポンスの型は proto設計ページ で定義したメッセージがそのまま使われる。

Handler → UseCase → Repository → Infrastructure の順に依存し、逆向きの依存は作らない

goroutine を使う工夫ポイントの例

func (u *TaskUseCase) GetDashboard(ctx context.Context, userID string) (*Dashboard, error)

「タスク一覧の取得」と「ユーザー情報の取得」を goroutine + sync.WaitGroup で並行実行し、両方揃ってから結合して返す。独立して実行できる処理を見つけたときに使う（無理に多用しない）。

直列：タスク取得(50ms) + ユーザー取得(30ms) = 80ms
並行：max(50ms, 30ms) = 50ms
