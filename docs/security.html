Security Requirements

セキュリティ要件
― 重要度ごとに何が必要かを決める ―

「悪用された場合の被害の大きさ」を基準に4段階に分け、各項目をこのアプリの構成（Gateway・Auth/User/Task Service・gRPC・Redis・MySQL・Docker Compose）に即して具体化しました。

Contents 読み方 必須（Critical） 重要（High） 推奨（Medium） 任意（Low）

00

重要度の読み方

「実装コストの高さ」ではなく「欠けたときの被害の大きさ」で4段階に分類しています。必須から順に対応してください。

必須 / CRITICAL

欠けるとなりすまし・情報漏洩など致命的な被害に直結する。この状態でのリリースは不可。

重要 / HIGH

欠けると深刻な被害につながり得る。初期リリース後、早い段階で対応する。

推奨 / MEDIUM

実装するとリスクをさらに下げられる、ベストプラクティス寄りの対策。

任意 / LOW

事業規模の拡大やコンプライアンス要件に応じて検討する発展的な対策。

01

MUST 必須（Critical）― これがないとリリースできない

必須要件

なりすまし・情報漏洩・他人のデータへの不正アクセスに直結する、実装必須の項目です。

認証

パスワードは bcrypt でハッシュ化して保存する

平文保存・可逆暗号化は禁止。User Service の CreateUser は password_hash のみを受け取り、ハッシュ化は Auth Service 側で完了させる。

認証

JWT の署名鍵はシークレットとして管理する

環境変数や Docker Secrets 経由で渡し、リポジトリにコミットしない。.env は必ず .gitignore に含める。

認可

リクエストの user_id と操作対象の user_id を必ず突き合わせる

Task/User Service は、トークンから取り出した user_id と操作対象のリソースの所有者が一致するか検証する。これを怠ると他人のタスクを閲覧・編集できてしまう（水平権限昇格）。

データ

SQL はプレースホルダを使い、文字列連結で組み立てない

database/sql の ? プレースホルダを必ず使用する。ユーザー入力を直接クエリ文字列へ埋め込まない（SQL インジェクション対策）。

インフラ

外部公開は Gateway のみに限定する

docker-compose 上で Auth/User/Task Service のポートを外部公開せず、内部ネットワークからのみ到達可能にする。

02

HIGH 重要（High）― 早い段階で対応する

重要要件

必須ほど即座に致命的ではないものの、放置すると深刻な被害につながる項目です。

認証

アクセストークンは短命にし、リフレッシュトークンと分離する

アクセストークンの有効期限は 15分程度に短く保ち、長期間有効なリフレッシュトークンとは別トークンとして扱う。漏洩時の被害範囲を限定する。

通信

Gateway にレート制限を実装する

特にログインエンドポイントへの総当たり攻撃（ブルートフォース）を防ぐため、IPやアカウント単位でリクエスト数を制限する。

通信

CORS の許可オリジンをホワイトリストで管理する

Gateway の CORS 設定でワイルドカード（*）を使わず、フロントエンドのドメインを明示的に列挙する。

データ

Redis のセッション情報に TTL を設定する

セッションキーには必ず有効期限を付与し、ログアウト後や期限切れ後にセッションが残り続けないようにする。

運用

GitHub Actions に依存脆弱性スキャンを組み込む

govulncheck や Dependabot を CI に組み込み、既知の脆弱性を含む依存ライブラリの混入を早期に検知する。

03

MED 推奨（Medium）― ベストプラクティス

推奨要件

必須・重要ほどの緊急性はないものの、実装しておくとリスクをさらに下げられる項目です。

監視

認証失敗・アクセス拒否を監査ログとして残す

構造化ログにリクエストIDを含め、ログイン失敗や認可エラーを追跡できるようにする。異常検知の土台になる。

認証

パスワードポリシーを導入する

最低文字数や既知漏洩パスワードとの照合（Have I Been Pwned 等）を Register 時に行う。

通信

gRPC の内部通信を mTLS で暗号化する

Gateway ⇔ 各サービス間の通信にも TLS（相互認証）を導入し、内部ネットワークが侵害された場合の盗聴・なりすましを防ぐ。

インフラ

Docker イメージは非 root ユーザーで実行する

マルチステージビルドで最終イメージを最小化し、コンテナ内のプロセスを非特権ユーザーで動かす。

04

LOW 任意（Low）― 発展的な対策

任意要件

事業規模の拡大やコンプライアンス要件に応じて、必要になった時点で検討すればよい項目です。

監視

異常なログイン試行・アクセスパターンを検知するアラートを設定する

通常と異なる地域からのログインや、短時間での大量アクセスを検知して通知する仕組みを導入する。

運用

定期的な脆弱性診断・ペネトレーションテストを実施する

サービスの規模や取り扱うデータの機微度に応じて、外部診断を定期実行する。

フロントエンド

ブラウザ向けセキュリティヘッダーを付与する

Content-Security-Policy や X-Content-Type-Options などを Gateway のレスポンスヘッダーに追加する。
