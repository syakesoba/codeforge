# Progate風 Goプログラミング学習サイト 要件定義（ドラフト）

## 1. 概要・目的
- Progateのような「ブラウザでスライド解説を読みながらコードを書いて即採点」形式の学習サイト
- 一般公開の本格運用サービスとして構築する
- 対象言語: **Go**（他言語経験者を想定し、基礎文法の説明は省略）
- スコープ: Goの**応用**分野に特化（Web開発・フレームワーク活用が中心）
  - REST API作成（net/http、Gin/Echoなどのフレームワーク）
  - データベース連携（database/sql、GORMなど）
  - 認証・JWTの実装
  - ゴルーチン・並行処理

## 2. コア機能
- ブラウザ上でコードを書いて実行・自動採点
- スライド形式の解説コンテンツ
- 進捗管理・学習ステータス（レッスン完了記録など）
- ログイン・ユーザー管理（メール＋パスワード認証）

## 3. 技術スタック
| 領域 | 選定 |
|---|---|
| バックエンド | Go |
| フロントエンド | React（Next.js） |
| コード実行方式 | サーバーサイドサンドボックス実行 |
| ホスティング | クラウド（AWS/GCP等）で本格運用を想定 |

## 4. 自動採点方式（提案）
Progateのような「標準出力の一致判定」では、REST API・DB・並行処理系の問題を正しく検証できないため、以下を提案します。

- **`go test` ベースの自動採点**を基本方式とする
  - 問題ごとに用意した非公開の `_test.go` を、ユーザーコードと一緒にサンドボックス内でビルド・実行し、テストの成否で採点
  - HTTPサーバー系の問題は、実際にポートを開いてサーバープロセスを起動するのではなく、`net/http/httptest`（`httptest.NewServer` / `httptest.NewRecorder`）を使ってテストコード内で完結させる
    - サンドボックス側でポート管理・プロセス間通信を扱う必要がなくなり、安全性・実装コストの両面で有利
  - ゴルーチン・並行処理の問題も、`go test` 内で `sync.WaitGroup` の利用やチャネルの送受信結果を検証する形にすれば、出力順序に依存しない安定した採点が可能
- サンドボックスはDockerコンテナ等で隔離し、CPU/メモリ/実行時間の制限を設ける

## 5. DB連携問題の環境（提案）
- **SQLite（インメモリ）** を採用
  - サンドボックスごとに瞬時に用意でき、外部プロセス（DBサーバー）の管理が不要
  - `database/sql` や GORM の使い方を学ぶ目的には十分
  - 本番相当のPostgreSQL/MySQLを扱う発展コースは、将来的な拡張として別途検討

## 6. コンテンツ管理
- MVPでは管理画面は作らず、**リポジトリ内にMarkdown/JSONでレッスン・問題をベタ打ち**して管理する

## 7. デザイン方針
- Progateに近い、ポップで親しみやすい雰囲気（キャラクター・バッジ等のゲーミフィケーション要素を含む）

## 8. マネタイズ
- 現時点では完全無料。将来の有料化は未検討（設計上は拡張の余地を残す程度に留める）

## 9. 未決定・今後詰める事項
- Goコースの具体的なレッスン数・出題順序（REST API→DB→認証→並行処理、の順で良いか等）
- ユーザーの学習進捗・バッジ等のデータモデル詳細
- サンドボックス実行基盤の具体的な構成（Docker Engine直叩き / gVisor / Firecracker等のセキュリティレベル）
- 開発の優先順位・マイルストーン（まずはコード実行・採点フローのPoCから作るのが妥当と思われる）
