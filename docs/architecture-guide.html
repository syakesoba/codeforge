リクエストの流れ

React は常に API Gateway だけを叩き、Gateway から先は gRPC で各サービスに振り分けます。フロントエンドが各サービスに直接アクセスしないことで境界を守ります。

React (TypeScript / ブラウザ)
HTTP + JWT
API Gateway Gin / Echo ・ JWT 検証
gRPC
Auth Service
User Service
Task Service
MySQL 永続化
Redis キャッシュ／セッション
HTTP/REST（外部公開・JSON） gRPC（内部通信・型安全・高速）

01

必要なコンポーネント

「サービス」「インフラ」「共通基盤」の3つに分けると全体像が把握しやすくなります。

区分コンポーネント役割
フロントエンドReact + TypeScriptブラウザ側 UI。API Gateway に HTTP(REST) でアクセス
ゲートウェイAPI Gateway (Gin/Echo)外部からの唯一の入口。認証チェック・ルーティング・レスポンス集約
サービスAuth Serviceログイン処理、JWT の発行・検証
サービスUser Serviceユーザー登録・情報管理（DB操作）
サービスTask Serviceタスクの CRUD（DB操作）
通信gRPC + Protocol BuffersGateway ⇔ 各サービスの型安全な内部通信
DBMySQLユーザー・タスクの永続化データ
キャッシュRedisセッション情報、頻出タスク一覧などの高速化
インフラDocker Compose全コンポーネントをコンテナとしてまとめて起動
ドキュメントOpenAPI (Swagger)Gateway が公開する REST API の仕様書
CI/CDGitHub Actionsテスト・Lint・ビルドの自動化

02

まとめ・次の一歩

→Gateway が交通整理役、Auth/User/Task は単機能に専念
→各サービス内部は Handler → UseCase → Repository → Infrastructure の一方向依存を守る
→context でタイムアウト／キャンセルを全層に伝搬させる
→goroutine は「並行実行できる処理」を見つけたときだけ使う

進み方

  1. proto ファイルの設計（各サービスの gRPC インターフェース定義） ― proto設計ページ に完了 ✓
  2. ディレクトリ構成・Clean Architecture の詳細は 実装ガイドページ を参照
  3. docker-compose.yml の構成（MySQL・Redis・各サービスの起動順）
  4. どのサービスから実装を始めるか（Auth Service から着手するのが一般的）
