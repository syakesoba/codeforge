詳細設計

サンドボックス実行の仕組み、API仕様、ディレクトリ構成、フロントエンドの構造をまとめる。

採点フローの詳細

  1. POST /api/problems/{id}/submit を受信し、internal/problems の許可リストで problemID を検証（パストラバーサル対策。未登録IDは404）
  2. os.MkdirTemp で一時ワークスペースを作成し、以下を配置
    • go.mod / go.sum（レッスンごとのファイルをそのままコピー。標準ライブラリのみのレッスンは module submission / go 1.22 だけの最小構成、Gin等を使うレッスンは go mod tidy で生成した内容）
    • solution.go（ユーザーコード）
    • solution_test.go（問題ディレクトリからコピーした非公開テスト）
  3. docker run をコンテナ名指定で起動し、go test -vet=off -json ./... を実行
  4. context.WithTimeout（30秒）超過時は docker rm -f で強制的にコンテナを削除
  5. 合否は go test プロセスの終了コードで判定する。go test -json の出力は表示用ログの整形にのみ使う
  6. ログイン中（有効なセッションCookieがある）かつ合格なら、progress テーブルに記録する
  7. defer os.RemoveAll でワークスペースを削除
合否判定に終了コードを使う理由

当初は go test -json のイベントに "Action":"fail" があるかどうかで判定していたが、 ゴルーチンからの保護されていないmap書き込み（fatal error: concurrent map writes）のように failイベントが出力される前にプロセスごと異常終了するケースを取りこぼす可能性があった。 go test は「全テストがpassしたときだけ終了コード0」という契約を守るため、判定はこちらを正としている。 Course「ゴルーチン・並行処理」Lesson 3はまさにこのケースを検出する問題になっている。

Dockerサンドボックスの実行設定

設定値目的
--networknone外部通信を完全に遮断。Gin等の外部モジュールはイメージビルド時に焼き込み済みのため、オフラインでも解決できる
--memory / --memory-swap512mメモリ枯渇の防止
--cpus0.5CPU占有の防止
--pids-limit64フォーク爆弾対策
--cap-drop ALL / --security-opt no-new-privileges―不要な権限の削除
非rootユーザー（イメージ内で USER judge）uid 1000コンテナ内権限の最小化
--rm + コンテナ名指定―実行のたびに使い捨て。タイムアウト時は名前を使って強制削除
実装時に判明した注意点

当初は --read-only + --tmpfs /tmp でファイルシステムを完全に固定する設計だったが、 これだと GOCACHE も毎回リセットされ、net/http が依存する標準ライブラリを コンテナ起動のたびにフルコンパイルすることになり、--memory 256m ではOOM Killが発生した。

対処として、Dockerイメージのビルド時に go build std を実行して標準ライブラリのビルドキャッシュをイメージ自体に焼き込む方式に変更（judge-image/Dockerfile）。 あわせて --read-only/--tmpfs は外し、コンテナは --rm で毎回破棄される使い捨てである点を踏まえて許容し、メモリ上限は512mに緩和した。

さらに go test はデフォルトで軽量な vet 解析を毎回走らせるが、これはイメージに焼き込んだキャッシュの対象外（コンテナの書き込み層はrmで消える）のため、実行のたびに数秒のロスが発生していた。 採点用途では静的解析は不要なため -vet=off を付けて解消した。これにより1リクエストあたり約1.5〜2秒まで短縮している。

外部モジュールを使うレッスンへの対応

Gin・GORM・SQLite・JWT・bcryptを使うコースでは、--network none のオフライン環境でも依存を解決できる必要がある。 そこで judge-image/priming/ にこれらを import するだけの捨てモジュールを置き、イメージビルド時に go mod tidy && go build ./... && go test -vet=off ./... を実行して モジュールキャッシュとビルドキャッシュをイメージに焼き込んでいる。各レッスンの go.mod/go.sum は、 このpriming時に解決されたものと同じバージョンを指す。実行時は GOPROXY=off を設定し、 万一バージョンが食い違っても外部への取得を試みず即座に失敗するようにしている。

go build だけでなく go test まで走らせる理由

当初はpriming時に go build だけ実行していたが、採点で実際に走るのは go test であり、 testing / httptest を含むテストバイナリのビルド経路はキャッシュ対象外だった。 そのためGinを使うレッスンの初回提出だけフルコンパイルが走り、15秒のタイムアウトに達していた。 priming時に実際のテストを1本走らせるようにして、初回5.9秒・以降2〜3秒に改善している。

認証と進捗の保存

サイト自体のログインはランダムトークンをHttpOnly Cookieで発行し、サーバー側の sessions テーブルと突き合わせる方式を採用している。 JWTはCourse「認証・JWT」の学習コンテンツとして扱うため、サイトの実装にはあえて使っていない（学習用の題材と本番実装を混同させないため）。

テーブルカラム用途
usersid, email, password_hash, created_at登録ユーザー。パスワードはbcryptでハッシュ化
sessionstoken, user_id, expires_atログインセッション（有効期間30日）
progressuser_id, problem_id, passed_at合格したレッスン。(user_id, problem_id)が主キーで重複しない
  • ログインは必須ではない。未ログインでも採点は利用でき、その場合の進捗はブラウザのlocalStorageにのみ保存される
  • ログイン中はサーバー側の進捗が正となり、フロントエンドは GET /api/progress の結果でチェックマークを表示する
  • 「ユーザーが存在しない」と「パスワードが違う」を区別せず、どちらも同じエラーを返す（登録済みメールアドレスの推測を防ぐため）。存在しないユーザーの場合もダミーハッシュとの照合を行い、応答時間の差からの推測も防いでいる
ローカル開発時のCookie設定

フロントエンド(:3000)とバックエンド(:8080)はポートが異なるためクロスサイト扱いになる。 本来は SameSite=None が必要だが、これは Secure（HTTPS）必須でローカル開発のhttpではCookieが拒否される。 そのため開発時は SameSite=Lax を使い、環境変数 SECURE_COOKIE=true を設定したときだけ Secure + SameSite=None に切り替わるようにしている。本番（HTTPS）では必ず設定すること。

API仕様

GET /api/problems/{id}

{
  "id": "web-api-basics-01",
  "title": "HTTPサーバーを立てる",
  "markdown": "# Lesson 1: ...",
  "starterCode": "package main\n..."
}

存在しない id の場合は 404。

GET /api/problems/{id}/answer

模範解答コードを返す。「答えを見る」ボタン押下時にフロントエンドから呼ばれる（初期表示のペイロードには含めず、明示的にリクエストされたときだけ返す）。

{ "code": "package main\n..." }

POST /api/problems/{id}/submit

リクエスト:

{ "code": "package main\n..." }

レスポンス:

{
  "passed": true,
  "output": "=== RUN   TestHelloHandler\n--- PASS: TestHelloHandler (0.00s)\nPASS\nok  \tsubmission\t0.003s",
  "durationMs": 1951
}

タイムアウト時は "passed": false と "error": "timeout" が付与される。

有効なセッションCookieが付いていて合格した場合は、あわせて進捗が記録される。

POST /api/auth/signup

リクエスト: { "email": "...", "password": "..." }

成功時は 201 で { "id": 1, "email": "..." } を返し、セッションCookieを発行する。

  • 400: メールアドレスの形式が不正、またはパスワードが8文字未満
  • 409: 既に登録済みのメールアドレス

POST /api/auth/login

リクエスト: { "email": "...", "password": "..." }

成功時は 200 で { "id": 1, "email": "..." } を返し、セッションCookieを発行する。失敗は一律 401。

POST /api/auth/logout

セッションを破棄しCookieを削除する。常に 204。

GET /api/me

ログイン中なら 200 で { "id": 1, "email": "..." }、未ログインなら 401。

GET /api/progress

ログイン中なら 200 で { "completedProblemIds": ["concurrency-01", ...] }、未ログインなら 401。

CORS

環境変数 FRONTEND_ORIGIN（デフォルト http://localhost:3000）で許可オリジンを指定。 セッションCookieをクロスオリジンでやり取りするため Access-Control-Allow-Credentials: true を返しており、 フロントエンド側も credentials: "include" を付けてリクエストしている。

react-markdownは生HTMLを描画しない

問題文のMarkdown内に生の <div> タグ等を書いても、rehype-raw を追加しない限り react-markdown は描画しない（黙って消える）。 注意書きなどを強調したい場合はMarkdown標準の引用（> ）を使うこと。Lesson 4の「重要な注意点」もこの理由で引用ブロックに書き直している。

セキュリティ上の考慮事項

  • 問題IDは許可リスト経由でのみディレクトリに解決（パストラバーサル対策）
  • 採点用テスト（solution_test.go）はサーバー側のみで扱い、クライアントに返さない
  • サンドボックスはネットワーク遮断・リソース制限・非root実行・使い捨てコンテナで隔離
  • Go側の context タイムアウトと、コンテナ名指定による強制削除の二重でハングを防止
  • 採点結果の出力は一定サイズで切り詰め、肥大化したログの返却を防止
  • パスワードはbcrypt（DefaultCost）でハッシュ化して保存し、平文は一切保持しない
  • セッショントークンは crypto/rand による32バイトの乱数。HttpOnly Cookieで発行し、JavaScriptからは読めない
  • ログイン失敗は「ユーザーが存在しない」「パスワードが違う」を区別せず一律 401。存在しないユーザーでもダミーハッシュとの照合を行い、応答時間からの推測も防いでいる
  • 期限切れセッションは参照時に検出して削除する
本番運用に向けて未対応の項目

現状はローカル開発向けの構成のため、公開前に少なくとも次の対応が必要: HTTPS化と SECURE_COOKIE=true の設定、CSRF対策（現在はCookie + SameSite=Lax のみ）、 ログイン試行のレート制限、同時採点数の制御（現在はリクエストごとに無制限にコンテナを起動する）、 アプリDBのSQLiteからPostgreSQL等への移行検討。
