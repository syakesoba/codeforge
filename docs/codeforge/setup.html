起動方法

ローカル環境でバックエンド・フロントエンドを立ち上げ、動作確認するまでの手順。

前提ソフトウェア

ソフト用途
GoバックエンドAPIサーバーのビルド・実行
Docker Desktop（Linuxコンテナモード）採点用サンドボックスの実行
Node.js / npmNext.jsフロントエンドの実行

初回セットアップ

  1. 採点用Dockerイメージをビルドする。標準ライブラリに加えてGin/GORM/SQLite/JWTのビルドキャッシュも焼き込むため、初回は数分かかる 
    docker build -t codeforge-judge:latest ./judge-image
  2. フロントエンドの依存パッケージをインストールする 
    cd frontend
npm install

起動

  1. バックエンドを起動する（リポジトリルートで実行。:8080で待受） 
    go run ./cmd/server
  2. フロントエンドを起動する（別ターミナルで。:3000で待受） 
    cd frontend
npm run dev
  3. ブラウザで http://localhost:3000 を開く

動作確認

  1. トップページに9つのコース（全47レッスン）が表示されることを確認する
  2. 任意のレッスンを開き、左側にスライド形式の解説、右側にコードエディタが表示されることを確認する
  3. 「次へ →」でスライドを送れること、「答えを見る」で模範解答が表示されることを確認する
  4. 雛形コードの TODO 部分を実装し、「実行して採点」を押す
  5. 数秒待つと「✅ 合格！」または「❌ 不合格」とgo testの出力が表示される。合格時は「おめでとうございます！」のポップアップから次のレッスンへ進める
  6. レッスン一覧に戻ると、合格したレッスンの右側にチェックマークが付いている

ログイン機能を確認する場合:

  1. ヘッダーの「新規登録」からメールアドレスとパスワード（8文字以上）で登録する
  2. 登録後、ヘッダーにメールアドレスと「ログアウト」が表示されることを確認する
  3. レッスンに合格し、ログアウト → 再ログインしても進捗（チェックマーク）が残っていることを確認する

ログインは必須ではない。未ログインでも採点は利用でき、その場合の進捗はブラウザのlocalStorageに保存される （そのブラウザでしか引き継がれない）。ログインすると進捗はサーバー側に保存される。

バックエンド単体をAPIとして直接叩いて確認したい場合:

curl http://localhost:8080/api/problems/web-api-basics-01

curl -X POST http://localhost:8080/api/problems/web-api-basics-01/submit \
  -H "Content-Type: application/json" \
  -d '{"code": "package main\n\nimport (\n\t\"fmt\"\n\t\"net/http\"\n)\n\nfunc helloHandler(w http.ResponseWriter, r *http.Request) {\n\tfmt.Fprint(w, \"Hello, CodeForge!\")\n}\n\nfunc main() {\n\thttp.HandleFunc(\"/hello\", helloHandler)\n\thttp.ListenAndServe(\":8080\", nil)\n}\n"}'

停止方法

Windowsでは Ctrl+C だけでは止まらないことがある

go run ./cmd/server は「go.exe（親）→ 実際にビルドされた server.exe（子）」という2階層のプロセスになっており、 npm run dev は「npm → next dev → start-server.js → Turbopackのワーカープロセス」という4階層になっている。 Windowsのコンソールでは Ctrl+C（CTRL_C_EVENT）が必ずしもプロセスツリー全体に伝わらず、 ターミナル上のプロセスだけが終了して実体（server.exe やNext.jsのワーカー）がバックグラウンドに残ることがある。 止めたつもりでもポートが解放されていない場合は、下記の方法で確実に停止すること。

まずは通常どおり、それぞれのターミナルで Ctrl+C を押す。そのあと必ずポートが解放されたか確認する。

netstat -ano | findstr ":8080 :3000"

まだ LISTENING が表示される場合は、プロセスツリーごと強制終了する。

OSポートからプロセスIDを調べるプロセスツリーを終了する
Windows netstat -ano | findstr :8080（フロントエンドは :3000）で一番右のPIDを確認 taskkill /F /T /PID <調べたPID>（/Tを忘れないこと。子プロセスごと終了する）
macOS / Linux lsof -i :8080（フロントエンドは :3000） kill <調べたPID>（効かなければ kill -9）

プロセスIDから親子関係を確認したい場合（Windows）:

wmic process where "name='node.exe' or name='go.exe' or name='server.exe'" get ProcessId,ParentProcessId,Name,CommandLine

最後に、念のためポートが解放されたことと、goとnode関連のプロセスが残っていないことを確認する。

netstat -ano | findstr ":8080 :3000"
tasklist | findstr /I "go.exe node.exe server.exe"

採点用のDockerコンテナは --rm 付きで起動しており、採点が終わる（またはタイムアウトする）と自動的に削除されるため、通常は手動で止める必要はない。念のため残存していないか確認したい場合:

docker ps -a --filter "name=judge-"

もし残っていた場合（異常終了時など）は次のコマンドで削除できる。

docker rm -f $(docker ps -aq --filter "name=judge-")

データの保存先

ユーザー・セッション・学習進捗は data/codeforge.db（SQLite）に保存される。 このファイルはバックエンドの初回起動時に自動生成され、.gitignore でバージョン管理から除外している。 データを初期化したい場合はサーバーを停止してからこのファイルを削除する。 

rm -rf data/

なお、ログインしていない状態での学習進捗はブラウザのlocalStorageに保存される（キー: codeforge:completed-lessons）。 こちらはブラウザの開発者ツールから削除できる。

トラブルシューティング

Windows + Git Bash から手動でdocker runする場合

Git Bash（MSYS）は /workspace のようなUnix風パスを自動でWindowsパスに変換してしまい、 docker run -v ... -w /workspace が意図通りに渡らないことがある。 手動でデバッグする場合は MSYS_NO_PATHCONV=1 を付けて実行する。 アプリ本体（Goの exec.Command 経由の呼び出し）はこの変換の影響を受けないため、通常運用では問題にならない。

採点が毎回タイムアウトする / 遅い

codeforge-judge イメージが標準ライブラリのビルドキャッシュを焼き込んだ最新版になっているか確認する（docker build -t codeforge-judge:latest ./judge-image を再実行）。 詳細は 詳細設計 の「実装時に判明した注意点」を参照。
