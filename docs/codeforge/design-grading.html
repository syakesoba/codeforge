採点フロー・サンドボックス

Dockerサンドボックスでの採点フロー、リソース制限の設定と調整の経緯、外部モジュール（Gin/GORM等）への対応。

詳細設計トップ 全体構成 採点フロー エディタ・学習体験 認証・進捗 API仕様 フロントエンド構成 セキュリティ

採点フローの詳細

  1. POST /api/problems/{id}/submit を受信し、internal/problems の許可リストで problemID を検証（パストラバーサル対策。未登録IDは404）
  2. os.MkdirTemp で一時ワークスペースを作成し、以下を配置
    • go.mod / go.sum（レッスンごとのファイルをそのままコピー。標準ライブラリのみのレッスンは module submission / go 1.22 だけの最小構成、Gin等を使うレッスンは go mod tidy で生成した内容）
    • solution.go（ユーザーコード）
    • solution_test.go（問題ディレクトリからコピーした非公開テスト）
  3. docker run をコンテナ名指定で起動し、go test -vet=off -json ./... を実行
  4. context.WithTimeout（30秒）超過時は docker rm -f で強制的にコンテナを削除
  5. 合否は go test プロセスの終了コードで判定する。go test -json の出力は表示用ログの整形にのみ使う
  6. ログイン中（有効なセッションCookieがある）かつ合格なら、progress テーブルに記録する
  7. defer os.RemoveAll でワークスペースを削除
合否判定に終了コードを使う理由

当初は go test -json のイベントに "Action":"fail" があるかどうかで判定していたが、 ゴルーチンからの保護されていないmap書き込み（fatal error: concurrent map writes）のように failイベントが出力される前にプロセスごと異常終了するケースを取りこぼす可能性があった。 go test は「全テストがpassしたときだけ終了コード0」という契約を守るため、判定はこちらを正としている。 Course「ゴルーチン・並行処理」Lesson 3はまさにこのケースを検出する問題になっている。

Dockerサンドボックスの実行設定

設定値目的
--networknone外部通信を完全に遮断。Gin等の外部モジュールはイメージビルド時に焼き込み済みのため、オフラインでも解決できる
--memory / --memory-swap768mメモリ枯渇の防止
--cpus1.0CPU占有の防止（下記コールアウト参照）
--pids-limit64フォーク爆弾対策
--cap-drop ALL / --security-opt no-new-privileges―不要な権限の削除
非rootユーザー（イメージ内で USER judge）uid 1000コンテナ内権限の最小化
--rm + コンテナ名指定―実行のたびに使い捨て。タイムアウト時は名前を使って強制削除
実装時に判明した注意点

当初は --read-only + --tmpfs /tmp でファイルシステムを完全に固定する設計だったが、 これだと GOCACHE も毎回リセットされ、net/http が依存する標準ライブラリを コンテナ起動のたびにフルコンパイルすることになり、--memory 256m ではOOM Killが発生した。

対処として、Dockerイメージのビルド時に go build std を実行して標準ライブラリのビルドキャッシュをイメージ自体に焼き込む方式に変更（judge-image/Dockerfile）。 あわせて --read-only/--tmpfs は外し、コンテナは --rm で毎回破棄される使い捨てである点を踏まえて許容し、メモリ上限は512mに緩和した。

さらに go test はデフォルトで軽量な vet 解析を毎回走らせるが、これはイメージに焼き込んだキャッシュの対象外（コンテナの書き込み層はrmで消える）のため、実行のたびに数秒のロスが発生していた。 採点用途では静的解析は不要なため -vet=off を付けて解消した。これにより1リクエストあたり約1.5〜2秒まで短縮している。

--cpus を0.5から1.0に引き上げた理由

当初 --cpus 0.5 で運用していたが、Gin/GORM等リンクが重いレッスンで採点時間が実測7〜23秒とばらつき、 まれに30秒のタイムアウトに達するケースがあった。--cpus 1.0 に引き上げたところ安定して6〜7秒になったため、 メモリにも余裕を持たせつつ（512m→768m）採用した。

外部モジュールを使うレッスンへの対応

Gin・GORM・SQLite・JWT・bcryptを使うコースでは、--network none のオフライン環境でも依存を解決できる必要がある。 そこで judge-image/priming/ にこれらを import するだけの捨てモジュールを置き、イメージビルド時に go mod tidy && go build ./... && go test -vet=off ./... を実行して モジュールキャッシュとビルドキャッシュをイメージに焼き込んでいる。各レッスンの go.mod/go.sum は、 このpriming時に解決されたものと同じバージョンを指す。実行時は GOPROXY=off を設定し、 万一バージョンが食い違っても外部への取得を試みず即座に失敗するようにしている。

go build だけでなく go test まで走らせる理由

当初はpriming時に go build だけ実行していたが、採点で実際に走るのは go test であり、 testing / httptest を含むテストバイナリのビルド経路はキャッシュ対象外だった。 そのためGinを使うレッスンの初回提出だけフルコンパイルが走り、15秒のタイムアウトに達していた。 priming時に実際のテストを1本走らせるようにして、初回5.9秒・以降2〜3秒に改善している。
