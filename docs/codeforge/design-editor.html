エディタのリアルタイムエラー検知・import自動修正

internal/lint パッケージが、エディタ入力に対するコンパイルエラー検知（/check）とimport自動修正（/format）を提供する。 どちらも採点用のDockerサンドボックスは使わず、バックエンドプロセスから直接 go build を実行する。

go build はDocker不要で安全な理由

go build はコンパイルのみでユーザーコードを一切実行しない（go run/go testと違い、 init() や main() が走らない）。そのためDockerによる隔離が無くてもホストへの影響はなく、 コンテナ起動オーバーヘッド（1〜2秒）が無いぶん、デバウンス方式でのリアルタイムに近い検知が可能になっている。 同時実行数は internal/lint 内のセマフォ（最大4並列）で制限し、大量の同時チェックでホストが詰まらないようにしている。

  • POST /api/problems/{id}/check: レッスンの go.mod/go.sum と提出コードを一時ワークスペースに配置し、go build ./... を実行。標準エラー出力を {file}:{line}:{col}: {message} でパースし、{"diagnostics": [{"line", "column", "message"}, ...]} を返す。隠しテストは含めない
  • POST /api/problems/{id}/format: golang.org/x/tools/imports（goimportsの実体）で未使用importの削除・不足importの追加・gofmt整形を行い、{"code": "整形後のコード"} を返す。任意でhints（後述）を受け付ける
goimportsが解決できないパッケージへのフォールバック

golang.org/x/tools/imports はパッケージ名からimportパスをヒューリスティックに推測するが、 gorm.io/gorm のように末尾の要素とパッケージ名が一致していても解決に失敗するケースが確認できた （モジュールキャッシュが揃っていても、対象レッスンのディレクトリから実行しても再現する、ツール側の既知の限界）。

対策として、imports.Process 実行後に残っている "undefined: X" を検知したら、 レッスンの go.mod の require 一覧を golang.org/x/mod/modfile でパースし、 importパスの末尾要素が X と一致するものを golang.org/x/tools/go/ast/astutil.AddImport で 直接注入するフォールバックを追加している（internal/lint/format.go の fillKnownImports）。 このフォールバックは残存エラーの検証に go build を1回実行する。

hints: /formatを高速化するヒント引き渡し

上記の fillKnownImports は正しく動くが、検証のたびに go build を実行するため、 Gin/GORM系レッスンでは1〜8秒程度（キャッシュ状況次第でばらつく）かかっていた。 一方、エディタは直前の/checkで既にどの識別子が未解決か把握している （LessonWorkspace.tsxのunresolvedImports）。この情報を/formatの リクエストボディに {"code": "...", "hints": ["gorm", "sqlite"]} として渡すと、 go buildによる再検証を丸ごとスキップし、go.modから直接解決する （internal/lint/format.goのinjectHintedImports）。

さらに、hints解決分のimportはimports.Processを呼ぶ前にASTへ直接注入している。 先に注入してしまえば、imports.Processは「未知の識別子を探して失敗する」という 一番コストの高い処理をしなくて済み、stdlibの解決と最終整形だけを1回で済ませられる （hints無しの場合は素直にimports.Processを1回呼ぶだけ）。

実測では、GORM/SQLite未解決のケースで 1.3〜8.4秒 → 常に0.3〜0.4秒程度まで短縮し、 かつgo build特有の実行時間のばらつきも無くなった。hintsを渡さない場合は 従来通りfillKnownImports（go buildによる検証）にフォールバックするため、 後方互換性は保たれている。

フロントエンドのlint統合

LessonWorkspace.tsx のCodeMirrorエディタに @codemirror/lint の linter() を組み込み、 入力停止後800msのデバウンスで自動的に /check を呼ぶ。診断は行・列からCodeMirrorの文字オフセットに変換し、 ガター表示＋該当箇所の下線で示す。

  • 応答が届く前に入力がさらに進んでいた場合は、送信時点のソースと現在のソースを比較して古い結果を破棄する（連番やrefは使わず、ドキュメント内容そのものを比較することで実現）
  • /checkの診断からundefined: Xの識別子一覧をunresolvedImportsとして状態管理し、エディタ下に常設の案内バー（「未解決のimportがあります」＋「インポートを自動修正」ボタン）を表示する。/format呼び出し時はこの一覧をhintsとして渡す
  • メッセージが undefined: で始まる診断には、VSCodeのクイックフィックスに相当する actions（「インポートを自動修正」）も付与している。押すと同じくhints付きで/formatを呼び、返ってきたコードでエディタ全体を置き換える。ただしCodeMirrorの診断ホバーは発見しにくいため、上記の常設バーが主な導線になっている
  • 常設の「フォーマット」ボタンからも、unresolvedImportsをhintsとして渡しつつ、いつでも明示的に同じ処理を呼び出せる
  • エディタのインデント単位は@codemirror/languageのindentUnit.of("\t")でタブに設定している。未設定だとCodeMirrorのデフォルト（スペース2つ）が使われ、gofmt準拠のタブインデントと改行後の字下げが視覚的に揃わなくなる

学習体験の向上（コード自動保存・進捗バー・ストリーク/バッジ）

  • コード自動保存: エディタの入力停止から1.2秒後に自動保存する（LessonWorkspace.tsx）。未ログイン時はlib/draft.ts経由でlocalStorageのみに保存し、ログイン中はlocalStorageとサーバー（code_draftsテーブル）の両方に保存する。レッスンを開いた際は、ログイン中はサーバーの下書きを優先し、無ければlocalStorage、それも無ければ雛形コードを表示する
  • 進捗バー: components/ProgressBar.tsxが汎用コンポーネント。サイトヘッダー（全27レッスン中の合格数）、コース一覧の各コースカード（コース内の合格数）、レッスンページのヘッダー（コース内の位置。例:「レッスン 3/6」）の3箇所に表示する
  • 連続学習日数（ストリーク）とバッジ: バッジ専用のテーブルは持たず、lib/streak.ts・lib/badges.tsが合格済みレッスンと合格日時（passedAt）からその場で導出する。ストリークは「今日 or 昨日まで連続で合格した日数」（Duolingo等と同じ、今日まだ学習していなくても連続記録を切らさない方式）。バッジは初回合格・コース制覇・全レッスン制覇・3日/7日連続の5〜7種類程度のシンプルな構成
未ログイン時のストリーク計算にも合格日時が必要

当初lib/progress.tsのlocalStorageは合格済みIDの配列のみを保持していたが、ストリーク計算には レッスンごとの合格日時が要る。保存形式を {"[problemId]": "ISO日時"} のオブジェクトに変更し、 旧形式（配列）が残っている場合は読み込み時に現在時刻を補完して移行する （過去の正確な合格日は失われるが、ストリークは今後の学習から数え直せば十分なため許容している）。
